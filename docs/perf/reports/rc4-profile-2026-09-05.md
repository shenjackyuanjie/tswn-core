# tswn_core 0.5.3：uProf 热点与 RC4 优化调查

日期：2026-09-05。基线 commit：`8635a36856b8e70f7dcd288baebabe126b3e2fa8`。

本轮先采样，再检查生成汇编，并测试前缀 KSA 内联、单链混合循环展开、独立 KSA 交错。
最终保留受伤被动计划的 `Vec → SmallVec<[_; 4]>` 改动：fixed30 单线程整体耗时 -1.77%，
核心 1v1/2v2 -2.64%。RC4 的生产实现保持原样；新增 `perf_runtime` example 供 fixed30、
score 和多队采样复跑。机器可读的逐轮时间、每 case 中位数及输入/二进制哈希见
[`rc4_20260905_profile.json`](../rc4_20260905_profile.json)。
原始二进制、PDB、采样数据、实验源码和逐轮输出在
`target/amduprof/20260905_hotpaths/`；该目录不入 Git。

## 环境与判定方法

- Ryzen 7 5800X，8 核 / 16 逻辑处理器，Windows 10 22H2；uProf 检测到 Microsoft Hyper-V。
- `rustc 1.98.0 (88d9e12ae 2026-08-18)`，LLVM 22.1.8；Cargo 1.98.0。
- `--release --features no_debug`，fat LTO、单 codegen unit、`debug=1`、默认 mimalloc，无 PGO。
- uProf 5.3.521.0，TBP 1 ms，用户态调用栈；采样不带 `--perf` / `--timed`。
- A 为当前 commit，B 仅把 `RC4::new_with_key_schedule_prefix` 的 `inline(never)` 改成
  `inline(always)`。每个 workload 先各预热一次，然后五轮 AB/BA 交替，取各自中位数。
- 小于 1.5% 的差异按噪声处理；采样时间只解释热点，不能当作吞吐提升。
- 三组初筛不带 `--perf`；扩展基准按 `benchmark-history.md` 的计时口径开启
  `--perf` / `--timed`。两种结果分开记录，不比较绝对值。

## 1. 实际热点

### fixed01，短局 1v1

600 万场；程序墙钟 26.716 s，采样 CPU 时间 26.545 s，2974489 胜。
以下为 self CPU_TIME 占进程总采样 CPU 时间的比例，包含编译器内联进该符号的代码：

| 归因位置 | CPU_TIME | 占比 |
| --- | ---: | ---: |
| `PreparedBattleRoster::refill_seed_state` | 4.300 s | 16.20% |
| `CombatRuntime::scan_plain_action_skill_probabilities` | 2.559 s | 9.64% |
| `RC4::new_with_key_schedule_prefix` | 2.112 s | 7.96% |
| `RuntimeRunner::run_to_completion_prevalidated` | 1.932 s | 7.28% |
| `PhaseScheduler::select_action` | 1.635 s | 6.16% |

调用栈确认：`reset_with_seed → refill_seed_state → new_with_key_schedule_prefix`。
`refill_seed_state` 的 inclusive 时间为 7.067 s / 26.62%，其中 KSA inclusive 为
2.219 s / 8.36%。不能把这些 inclusive 数字再与上面的 self 相加。

`refill_seed_state` 内的主要归因是：

- `rng.js_xor_str(&state.rc4_key)`：1.670 s；
- `rng.encrypt_bytes_no_change(&self.id_key_names[*player])`：2.161 s。

两处字节混合加上独立 KSA 的 self 时间，共占约 22.4%。因此这个输入里初始化真正值得看的是
RC4 运算，而非先改 `Vec::clear` 或排序。战斗过程的 RC4 已内联进技能、调度和目标选择，
22.4% 不是 RC4 的全程序总占比。

技能扫描函数也有类似归因陷阱：1.420 s 实际落在内联的 `select_plain_assassinate_targets`
调用行，约占该符号 self 的 55.5%。不能将全部 9.64% 都归因于扫描技能表。

### fixed12，8 人 FFA

通过公开 `runtime_groups_win_rate` API 跑 40 万场，输入确认为八个单人队；
程序墙钟 16.255 s，采样 CPU 时间 16.200 s，72893 胜，errors / guard 均为 0。

| 归因位置 | CPU_TIME | 占比 |
| --- | ---: | ---: |
| `run_to_completion_prevalidated`，包含内联行动循环 | 2.863 s | 17.67% |
| `scan_plain_action_skill_probabilities` | 2.272 s | 14.02% |
| `skill_hook_plan` | 1.090 s | 6.73% |
| `refill_seed_state` | 0.858 s | 5.30% |
| `select_plain_default_attack_target` | 0.735 s | 4.54% |

其中暗杀目标选择调用行占 1.169 s / 7.22%；两处初始化字节混合分别为 0.380 s、
0.401 s。多人局更应关注行动、选目标和 hook，不应从短局推断所有输入都受初始化支配。

两个采样入口的宿主 binary 不同，fat LTO 的内联归因也可能不同；表格用于各自内部排序。
TBP 的指令位置会有采样偏移，不能据此断言某一条 store 有确定的缓存未命中或流水线停顿。

## 2. RC4：哪些方案值得做

### 内联与局部状态：已经做得比较充分

`next_u8_untracked` 已经 `inline(always)`，用 u8 约束索引并移除边界检查。
基线汇编中 `js_xor_str` 和名字混合的内循环没有逐字节函数调用，`i/j` 保持在寄存器里，
循环结束才写回。重复加 inline 或把 `self.i/j` 搬到局部变量缺乏明确机会。

前缀 KSA 仍是独立函数，存在 256 字节临时状态的复制，因此实际构建并测试了强制内联版本。
重采样后独立 KSA 符号从热点表消失，时间归入 `refill_seed_state`，这只是归因变化；
收益必须看下方 A/B。

### 单条状态链直接 SIMD：不作为首选

这份实现每轮通过 `S[i] → j → S[j] → swap → S[si+sj]` 形成依赖。
而 `js_xor_str` / 名字混合还把当前密文字节反馈到下一轮 `j`，不是普通 RC4 输出流的独立 XOR。
即使把输出 XOR 改成向量指令，也消不掉这条主要依赖链。

AVX2 的 gather 接口以 32/64 位元素为单位，不能直接等价替换当前字节表的随机读写。
需要重新设计数据布局并实测成本，不能仅凭“256 位寄存器一次八路”推断更快。
指令接口参考 [Intel gather 文档](https://www.intel.com/content/www/us/en/docs/cpp-compiler/developer-guide-reference/2021-8/intrinsics-for-gather-operations.html)。
[OpenSSL RC4 汇编](https://github.com/openssl/openssl/blob/master/crypto/rc4/asm/rc4-x86_64.pl)
也区分表元素宽度、循环展开和 CPU 特定调度；其历史速度数据不能外推到本机 Zen 3，
更不能直接套用于这里的额外 `j` 反馈语义。

### 单链循环展开：本轮原型没有收益

在独立微基准中按 2/4/8 字节展开同一混合循环。原型调用 `next_u8`，编译时启用
`no_debug`，因此对应相同的无探针 PRGA；逐项比对长度 0..300、连续三次混合后的完整 S-box
和 i/j。计时使用同一条约 80 字节的含中文输入，每轮 200 万次连续混合。

| 展开数 | 原循环中位数 | 展开后中位数 | 耗时变化 |
| --- | ---: | ---: | ---: |
| 2 | 0.645712 s | 0.666738 s | +3.26% |
| 4 | 0.642129 s | 0.670234 s | +4.38% |
| 8 | 0.663273 s | 0.683774 s | +3.09% |

这是特定原型的内核结果，不代表所有手写汇编展开方案均不可行；本轮没有将它接入生产路径。

### 独立对局的 2～4 路交错：最值得继续验证

直接复用仓库已有 `RC4::update_interleaved`，比较顺序完成各 lane 与逐步交错推进。
每轮 50 万组独立状态，完整一轮 256 步 KSA；输入为同长度、不同数字 seed 的约 50 字节 key。
包含状态重置，结果与逐路实现逐字节相同。首轮预热后五轮交替中位数：

| lane 数 | 逐路执行 | 交错执行 | 内核耗时变化 |
| --- | ---: | ---: | ---: |
| 2 | 0.572571 s | 0.336536 s | -41.22% |
| 3 | 0.842117 s | 0.420554 s | -50.06% |
| 4 | 1.161448 s | 0.485254 s | -58.22% |

这是标量指令级并行，不是已经实现的 SIMD 战斗执行器，也不是整场胜率提升。
微基准没有包含生产前缀检查点、排序、完整 seed 初始化或不同长度 key。

建议下一步在 worker 内预备 2～4 场独立 seed 的 RC4 状态，交错 KSA 后仍按原场次运行战斗。
随后可扩展到 key/name 混合循环；比分支复杂的整场战斗 SIMD 更容易控制改动范围。
必须保留第 0 场无 seed、seed 数字位数变化、前缀不命中、尾部不足 lane 数、每场独立 RNG
状态与相同战斗顺序。已有交错路径在 score 名字构造中使用，当前胜率 seed 路径仍逐场初始化。

## 3. 扩展 A/B

初筛不计时口径，CLI 单线程：fixed01 / 120 万场耗时 -0.51%，fixed23 / 50 万场 -1.25%，
fixed28 / 40 万场 -0.81%，均未越过噪声带。fixed28 为保持队伍含义，仅把队内换行转换成
CLI 的 `++` 分隔并传 `--double-plus`；原始 fixed30 文件未改写。

随后扩展到 `benchmark-history.md` 的两种长期样本、fixed30 全集、现存 score 输入。
下表开启逐场计时，每项五轮交替中位数；负数表示 B 的耗时缩短：

| workload | A / s | KSA 强制内联 B / s | 变化 |
| --- | ---: | ---: | ---: |
| fixed30 单线程，30 × 13000 | 10.383961 | 10.481355 | +0.94% |
| aaa/bbb 单线程，100 万 | 5.689 | 5.696 | +0.12% |
| 复杂样本单线程，100 万 | 8.506 | 8.542 | +0.42% |
| fixed30 自动线程，30 × 13000 | 1.289114 | 1.325930 | +2.86% |
| aaa/bbb 自动线程，100 万 | 0.732 | 0.714 | -2.46% |

| score mario，13000 | 0.549968 | 0.558342 | +1.52% |

fixed30 单线程分组变化：core 1v1/2v2 -0.56%、1v1 +0.42%、2v2 -0.15%、
stress_multi +1.24%。自动线程结果波动更大，只有 aaa/bbb 为正收益，另有负收益项，

每 13000 场有 3 次，两边均相同，其余 case 没有 guard。没有改写 corpus 或用旧版本历史
绝对时间判断当前改动收益。OpenBox 六档端到端 CQP/CQD 不属于本轮 core 候选的测量范围。

### 最终采用：受伤被动计划使用 SmallVec

在 `runtime/combat/passive.rs` 中，将 `drain_plain_post_damage_skill_chain_into` 的
临时计划从 `Vec` 改为 `SmallVec<[_; 4]>`。少量钩子快照不再申请堆内存，超过四项仍可扩展；
排序、等级快照和钩子执行逻辑使用原有代码。

候选二进制保存在 `smallvec/`，与原始基线重新做一套完整的五轮交替 A/B，原始输出是
`smallvec_ab.json`。下表不是与上一个时段的内联候选作比较：

| workload | A / s | SmallVec B / s | 耗时变化 |
| --- | ---: | ---: | ---: |
| fixed30 单线程 | 10.431417 | 10.246427 | **-1.77%** |
| aaa/bbb 单线程，100 万 | 5.632 | 5.642 | +0.18%，噪声 |
| 复杂样本单线程，100 万 | 8.426 | 8.434 | +0.09%，噪声 |
| fixed30 自动线程 | 1.258894 | 1.238190 | **-1.64%** |
| aaa/bbb 自动线程，100 万 | 0.661 | 0.651 | -1.51%，接近阈值 |
| 复杂样本自动线程，100 万 | 1.006 | 0.993 | -1.29%，噪声 |
| score mario，13000 | 0.552125 | 0.541792 | **-1.87%** |
| score CQP 单人，20 × 1000 | 0.882195 | 0.885645 | +0.39%，噪声 |

fixed30 按每轮分组总时间取中位数，单线程核心 1v1/2v2 从 13.0980 降至 12.7518 µs/场
（-2.64%），其中 1v1 -2.98%、2v2 -2.43%。自动线程核心组 -3.04%。
stress_multi 单线程 -1.33%、自动线程 -1.19%，没有越过噪声带。
逐 case 的单线程中位数最大正向变化只有 +0.04%，没有被整体聚合掩盖的明显退化。
所有轮次的逐 case 胜场、errors、guard 均与基线一致。

同一 fixed01、600 万场、单线程、无 `--perf` 的重采样中，受伤被动计划调用链的 inclusive
归因从 1.610 s / 6.07% 降至 1.186 s / 4.56%，原先由该调用链触发的 `mi_malloc_aligned`
不再进入前 40 项。该函数的 self 反而从 0.534 s 增至 0.722 s，说明只看单个函数的 self
排序会误判；应结合调用栈和 A/B。重采样胜场仍为 2974489/6000000。

## 4. RC4 之后的候选

1. **暗杀及默认攻击的目标选择。** 暗杀调用行在两个 workload 都突出。优先减少重复构造
   `enemy_skip_indices`、重复实体查询和重复队伍计数；不能为了“只剩一个敌人”而跳过
   原有重复抽样及 RNG 消耗。`alive_group_len_containing` 的线性查找也有可见归因。
2. **技能变动后重建 hook / action 缓存。** FFA 的 `skill_hook_plan` 占 6.73%，其中慢速分支
   的技能等级判断、registry 查找和 hook mask 检查都有样本。源码中 `merge_level_at`
   会让缓存失效，`prepare_hook_cache` 的生产调用在初始化处；可以评估下一次行动时按 generation
   重建一次，避免变更后持续回退扫描。必须保留执行中的快照及动态技能顺序语义。
3. **受伤被动计划的临时 Vec，已完成本轮优化。** 调用栈把 `mi_malloc_aligned` 归因到
   `drain_plain_post_damage_skill_chain_into` 的收集路径；本轮用 SmallVec 消除常见小快照的
   堆分配，实测结果见上节。

前两项仍是源码与采样支持的候选，尚未修改或确认收益。

uProf 5.3 的 `report --detail` 默认只列十项，且必须另外带 `-g` 才输出调用栈。
本轮 `--disasm-full --cutoff 40` 曾生成含损坏尾部的文件，因此仅提取与独立
`llvm-objdump` 核对的 RC4 地址区段使用，完整统计依据普通 detail / callstack 报告。
文档 `amd-uprof.md` 和 `rule.md` 已补上 `report -g`。

```powershell
cargo build -p tswn_core --release --features no_debug --bin tswn-cli --example perf_runtime
AMDuProfCLI.exe collect --config tbp -g -o target/amduprof/new_case01 `
  target/release/tswn-cli.exe bench win-rate `
  -f docs/perf/fixed_cases_30/01_1v1-6a2ace7473581042.txt -n 6000000 -s
AMDuProfCLI.exe report -i target/amduprof/new_case01 --detail -g --cutoff 40
AMDuProfCLI.exe collect --config tbp -g -o target/amduprof/new_ffa12 `
  target/release/examples/perf_runtime.exe `
  -i docs/perf/fixed_cases_30/12_ffa_8-f9ed6e2bccd03417.txt -n 400000 --threads 1
AMDuProfCLI.exe report -i target/amduprof/new_ffa12 --detail -g --cutoff 20
```

独立微基准构建参数为 `rustc --edition 2024 --cfg 'feature="no_debug"'
-C opt-level=3 -C lto=fat -C codegen-units=1 -C debuginfo=1`，没有开启 native CPU / AVX2。

  lib 1 项及 doctest 7 项按原有配置忽略，无失败。
- `cargo test -p tswn_test --features runtime-corpus --test runtime --release`：124/124 通过，
